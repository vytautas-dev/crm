# Owner-scoped Persistence + RLS Convention Baseline — Implementation Plan

## Overview

Establish the persistence foundation (F-01) that every later slice depends on: wire
Supabase migration tooling into the repo, ship the reusable DB primitives and an
owner-scoped, per-operation RLS policy convention, expose a typed DB client, and prove
the isolation pattern with an automated two-user test. This is a **minimal enabler**,
not a schema build-out — no `companies`, `tasks`, or content tables are created here;
they arrive with their own slices and reuse this convention.

## Current State Analysis

- **Migration tooling is half-present.** `supabase` CLI is a devDependency (`^2.23.4`),
  `supabase/config.toml` exists with `[db.migrations] enabled = true` and `major_version = 17`,
  but there is **no `supabase/migrations/` directory, no migrations, and no npm scripts**
  for the workflow. `supabase/` currently holds only `config.toml` and `.gitignore`.
- **Auth/RLS substrate is ready.** `src/lib/supabase.ts` builds a cookie-based SSR client
  with the **anon key** (`@supabase/ssr`), so a signed-in user's JWT flows to Postgres and
  `auth.uid()` is the natural ownership key — RLS does the isolation. `src/middleware.ts`
  already resolves `context.locals.user`.
- **The client is untyped.** `createServerClient(...)` (`src/lib/supabase.ts:9`) has no
  `<Database>` generic and there is no generated types file.
- **The convention exists only as prose.** `CLAUDE.md` states "always enable RLS… granular
  per-operation, per-role policies" and the migration naming format `YYYYMMDDHHmmss_short_description.sql`.
  F-01 turns that prose into an executable, copy-paste template + a verified, reusable trigger.
- **No test runner exists.** `package.json` has no test framework; CI (`.github/workflows/ci.yml`)
  runs lint + build only.
- **PG 17** provides `gen_random_uuid()` in core — no `pgcrypto`/`uuid-ossp` extension needed.

## Desired End State

After this plan:

- `supabase/migrations/` exists and contains one migration: a reusable `public.set_updated_at()`
  trigger function. `npm run db:reset` applies it cleanly against the local stack.
- A typed DB pipeline exists: `npm run db:types` regenerates `src/db/database.types.ts`, and
  `src/lib/supabase.ts` uses `createServerClient<Database>(...)`. `npm run typecheck` and `npm run build` pass.
- `docs/reference/rls-convention.md` is the single canonical source future slices copy from:
  the owner-scoped column block, the four per-operation policies, trigger usage, and how to verify.
- `npm test` runs a Vitest integration test that, against a running local stack, applies a
  throwaway canary table built from the convention template, signs in two real users, and proves
  user A cannot SELECT/UPDATE/DELETE user B's rows — then tears everything down. No throwaway
  schema objects remain.

Verification: `npm run db:reset`, `npm run db:types` (no diff churn beyond expected), `npm run lint`,
`npm run build`, and `npm test` (with `supabase start` running) all succeed.

### Key Discoveries:

- Anon-key SSR client (`src/lib/supabase.ts:9`) ⇒ RLS keyed on `auth.uid()` is the enforcement path; the test must exercise that real path, not a simulated one.
- `config.toml` already enables migrations and pins PG 17 — no extension migration needed for UUIDs.
- CLAUDE.md migration naming contract: `supabase/migrations/YYYYMMDDHHmmss_short_description.sql` (generated by `supabase migration new`).
- The test needs DDL (create/drop canary) that the anon client cannot perform → a direct Postgres admin connection (`pg`) handles setup/teardown; supabase-js anon clients handle the user-scoped assertions.

## What We're NOT Doing

- **No entity tables** (`companies`, `tasks`, `content_submissions`, `profiles`) — those belong to S-01/S-02.
- **No Storage bucket RLS** — deferred to S-02 (file uploads).
- **No service-role / bypass-RLS write path** — deferred to F-02 (background jobs).
- **No seed data convention** (`supabase/seed.sql`) — nothing to seed yet.
- **No CI wiring of the DB test** — the canary test is a local gate this change establishes; running it in GitHub Actions (spinning Supabase in CI) is a deliberate follow-up.
- **No OAuth / auth changes** — auth is already present per the baseline.

## Implementation Approach

Three phases, each independently verifiable, in dependency order: (1) tooling + the one
permanent DB primitive + typed client, so the workflow exists; (2) the documented template
and canary fixture, so there is a canonical thing to copy and to test against; (3) the
automated isolation test that consumes the fixture and proves the pattern. The reusable
`set_updated_at()` function is the only permanent DB object; the canary table lives only
for the duration of the test.

## Critical Implementation Details

- **Test isolation lifecycle.** The canary test owns full setup/teardown: it must create the
  table + policies + trigger before the user-scoped assertions and drop them (and delete the
  two test users) in teardown, even on assertion failure (`afterAll`/`finally`). A leaked canary
  table or test user would pollute the local DB and make reruns flaky.
- **Two distinct auth contexts.** Isolation can only be proven with two *separate* signed-in
  supabase-js clients (one per user), each created with the anon key and its own session — not
  one client with `auth.uid()` swapped. Use the service-role key only for admin user creation
  (`auth.admin.createUser` with `email_confirm: true`) and the `pg` admin connection only for DDL.
- **`default auth.uid()` on `user_id`.** The template sets `user_id` default to `auth.uid()` so
  inserts are owner-safe even if the client omits it; the INSERT policy's `WITH CHECK` still
  enforces `auth.uid() = user_id` so a forged `user_id` is rejected.

## Phase 1: Migration tooling + reusable DB primitives

### Overview

Make the Supabase migration workflow real in this repo, ship the shared `set_updated_at()`
trigger function, and wire a typed DB client.

### Changes Required:

#### 1. Reusable updated_at trigger function

**File**: `supabase/migrations/<ts>_create_set_updated_at_function.sql` (generated via `npm run db:new set_updated_at_function`)

**Intent**: Create the one permanent, reusable DB primitive of this baseline — a trigger
function every owner-scoped table attaches to keep `updated_at` current at the DB layer.

**Contract**: Defines `public.set_updated_at()` returning `trigger`, setting `NEW.updated_at = now()`.
Non-obvious detail — pin the function's `search_path` to avoid mutable-search-path warnings:

```sql
create or replace function public.set_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;
```

#### 2. DB workflow npm scripts

**File**: `package.json`

**Intent**: Expose a single discoverable migration/types workflow future slices reuse.

**Contract**: Add scripts — `db:new` → `supabase migration new`, `db:reset` → `supabase db reset`,
`db:types` → `mkdir -p src/db && supabase gen types typescript --local > src/db/database.types.ts` (the `mkdir -p` makes it robust on a fresh checkout where `src/db/` doesn't exist yet), and
`typecheck` → `astro check` (`@astrojs/check` is already a devDependency; `astro build` does *not*
typecheck TS, so this is the real type gate). (The `test` script is added in Phase 3.)

#### 3. Generated Database types

**File**: `src/db/database.types.ts`

**Intent**: Commit the initial generated `Database` type so the typed-client pipeline is wired now;
S-01 reruns `db:types` to populate it with real tables.

**Contract**: Output of `supabase gen types typescript --local`. Exports a `Database` type
(`public.Tables` will be empty until the first entity slice). Do not hand-edit.

#### 4. Typed SSR client

**File**: `src/lib/supabase.ts`

**Intent**: Pass the generated `Database` generic to the client so all later query builders are typed.

**Contract**: `createServerClient(...)` → `createServerClient<Database>(...)`, importing `Database`
from `@/db/database.types`. Null-return-on-missing-env behavior is unchanged.

### Success Criteria:

#### Automated Verification:

- Local stack starts: `npx supabase start`
- Migration applies cleanly: `npm run db:reset`
- Types regenerate without error: `npm run db:types`
- Type checking passes: `npm run typecheck` (astro check) and build succeeds: `npm run build`
- Linting passes: `npm run lint`

#### Manual Verification:

- `supabase/migrations/` contains exactly the trigger-function migration; `set_updated_at()` is visible in Studio (`http://localhost:54323`).
- `src/db/database.types.ts` exists and exports `Database`; `src/lib/supabase.ts` compiles with the generic.

## Phase 2: RLS convention — template + reference doc

### Overview

Capture the owner-scoped table convention as the canonical copy-paste source and as the
fixture the Phase 3 test applies.

### Changes Required:

#### 1. RLS convention reference doc

**File**: `docs/reference/rls-convention.md`

**Intent**: The single source future slices grep/copy when adding an owner-scoped table —
columns, the four per-operation policies, trigger wiring, and the verification recipe.

**Contract**: Documents the standard owner-scoped table shape and the four policies for the
`authenticated` role keyed on `auth.uid() = user_id`. The canonical SQL block (load-bearing —
every future table depends on it):

```sql
-- Standard owner-scoped table
create table public.<entity> (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade default auth.uid(),
  -- ...entity columns...
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

alter table public.<entity> enable row level security;

create trigger set_<entity>_updated_at
  before update on public.<entity>
  for each row execute function public.set_updated_at();

create policy "<entity>_select_own" on public.<entity>
  for select to authenticated using (auth.uid() = user_id);
create policy "<entity>_insert_own" on public.<entity>
  for insert to authenticated with check (auth.uid() = user_id);
create policy "<entity>_update_own" on public.<entity>
  for update to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "<entity>_delete_own" on public.<entity>
  for delete to authenticated using (auth.uid() = user_id);
```

The doc also states: RLS-on + no `anon` policy ⇒ anon denied by default (no explicit deny needed);
and the "how to verify" pointer to `npm test`.

#### 2. Canary fixture SQL

**File**: `supabase/tests/fixtures/canary_table.sql` (consumed by the Phase 3 test)

**Intent**: A throwaway instantiation of the template (`public.canary`) the test applies and drops,
so the test verifies the *actual* documented template, not a divergent copy.

**Contract**: The SQL block above with `<entity>` = `canary` and no extra entity columns. Idempotent-friendly (the test drops before/after).

#### 3. CLAUDE.md pointer

**File**: `CLAUDE.md`

**Intent**: Point readers/agents at the new canonical doc from the existing RLS prose.

**Contract**: One-line reference to `docs/reference/rls-convention.md` added near the existing
"Always enable RLS on new tables…" convention bullet. No full SQL template inlined (keeps always-loaded instructions lean).

### Success Criteria:

#### Automated Verification:

- Linting/formatting passes: `npm run lint`
- Format check passes: `npm run format`

#### Manual Verification:

- `docs/reference/rls-convention.md` renders correctly and the SQL block matches the fixture.
- CLAUDE.md pointer resolves to the new doc.

**Implementation Note**: Pause for manual confirmation before proceeding.

## Phase 3: Automated isolation verification (Vitest canary)

### Overview

Add a test runner and a two-real-user integration test that proves the RLS convention isolates
data, run against the local stack.

### Changes Required:

#### 1. Test runner + DB driver dependencies

**File**: `package.json`

**Intent**: Establish Vitest (the JS test runner slices will reuse) and `pg` (for setup/teardown DDL the anon client can't perform).

**Contract**: Add devDeps `vitest`, `pg`, `@types/pg`. Add `test` → `vitest run` and `test:watch` → `vitest`.

#### 2. Vitest config

**File**: `vitest.config.ts`

**Intent**: Configure Vitest for a node-environment integration test.

**Contract**: Node test environment; include `tests/**/*.test.ts`. No mocking — this is an integration test against the live local stack. Ensure the tsconfig `include` covers `tests/` so `npm run typecheck` (astro check) type-checks the test file (Vitest itself runs via esbuild and does not typecheck).

#### 3. Test environment inputs

**File**: `.env.example` (and a note in `README.md` / the convention doc)

**Intent**: Declare the inputs the test needs from `supabase start` output.

**Contract**: Document `SUPABASE_URL`, `SUPABASE_KEY` (anon), `SUPABASE_SERVICE_ROLE_KEY`, and
`SUPABASE_DB_URL` (e.g. `postgresql://postgres:postgres@127.0.0.1:54322/postgres`). The test reads these from the environment.

#### 4. Canary isolation test

**File**: `tests/rls-canary.test.ts`

**Intent**: Prove the documented template enforces per-user isolation end-to-end via the real anon-key/JWT path.

**Contract**: Lifecycle and assertions —
- `beforeAll`: open a `pg` admin connection (`SUPABASE_DB_URL`), drop+apply `supabase/tests/fixtures/canary_table.sql`; via service-role supabase client, `auth.admin.createUser({ email_confirm: true })` for user A and user B.
- Build two anon-key clients, `signInWithPassword` as A and B respectively.
- Assert: A inserts a row (succeeds); A selects → sees its row; **B selects → empty array**; **B update of A's row → chain `.select()`, assert returned array is empty**; **B delete of A's row → chain `.select()`, assert returned array is empty**; **read back as A → row still present with field values unchanged** (this read-back is the real isolation check — a silently-filtered UPDATE/DELETE returns no error, so do NOT assert via thrown errors); an insert by B with `user_id` forced to A's id → rejected by `WITH CHECK` (this case *does* error).
- `afterAll` (always runs): delete users A and B; `drop table if exists public.canary cascade`; close the `pg` connection.

### Success Criteria:

#### Automated Verification:

- Local stack running: `npx supabase start`
- Test passes: `npm test`
- Linting passes: `npm run lint`
- Type checking passes: `npm run typecheck`

#### Manual Verification:

- After `npm test`, the local DB contains **no** `public.canary` table and **no** leftover test users (verify in Studio).
- Temporarily weakening a policy (e.g. changing the SELECT policy to `using (true)`) makes the test fail — confirming the test actually guards isolation.

**Implementation Note**: Pause for manual confirmation; this is the phase that proves the binding privacy guardrail.

## Testing Strategy

### Unit Tests:

- None — this baseline has no business logic to unit-test. The trigger function and policies are verified via the integration test.

### Integration Tests:

- `tests/rls-canary.test.ts` — two-user isolation across SELECT/INSERT/UPDATE/DELETE on a canary table built from the canonical template (the regression guard future slices extend).

### Manual Testing Steps:

1. `npx supabase start`, then `npm run db:reset` — confirm clean apply.
2. `npm test` — confirm the canary test passes and tears down (Studio shows no `canary` table / test users).
3. Weaken a policy in the fixture, rerun `npm test`, confirm failure; revert.

## Performance Considerations

None — `low`/`small` target scale (PRD). The `set_updated_at` trigger is per-row on update and negligible.

## Migration Notes

Greenfield schema — no existing data to migrate. The trigger-function migration is additive and safe to apply to a fresh local DB.
